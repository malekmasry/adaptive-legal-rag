Эксперимент codex/dialogue-memory
Основа: dev_if_test, 5d7f10d (сообщённый результат 35/100).
Ветка не содержит ни мультизапроса, ни новых чанков, ни нового стеммера.
Сохраняются прежние BM25, 342 чанка, векторный индекс, реранкер, порог 0,5,
генерационный промпт и бюджеты. Меняются подготовка вопроса и управление диалогом.

ДВА ФОРМАТА РАБОТЫ

1. Платформа: каждая строка id,question — независимый тест-кейс.
Организатор передаёт историю прямо в question:
Пользователь: Какой гарантийный срок по П-17/2024?
Ассистент: Уточните.
Пользователь: Ответь на предыдущий вопрос.

LegalAssistant.answer(question) разбирает эту историю локально для запроса.
Генератор получает всю переданную историю; поиск и реранкер получают
восстановленный вопрос «Какой гарантийный срок по П-17/2024?».
Между ID память НЕ переносится: это прямо запрещено форматом проверки.
Один engine можно безопасно использовать для параллельных независимых строк.

2. Последовательный чат: создаётся отдельная сессия для каждого диалога.

engine = LegalAssistant(archive_path)
chat = engine.new_session()
first = chat.ask("Какой гарантийный срок по П-17/2024?")
second = chat.ask("Повтори ответ")
third = chat.ask("Ответь на предыдущий вопрос")
chat.clear()

Объект chat хранит реальные пользовательские реплики и ответы. Индекс engine
может быть общим, но историю два объекта chat друг с другом не разделяют.
Сессия сериализует свои запросы собственным lock. Другие сессии независимы.
Сохраняется до 6 обменов и 16000 символов (настраивается при создании сессии).
Старые обмены удаляются целиком: цитаты и условия не обрезаются посередине.
Память живёт в процессе. После clear(), завершения чата или перезапуска процесса
она не сохраняется. Автоматической записи личной переписки на диск нет.
Если память вытеснила нужную реплику, система просит повторить вопрос.

CLI
python pipeline_cli.py --chat --archive PATH_TO_KB.zip --embeddings --ask-key
API-адреса и модели берутся из прежнего окружения.
Чтобы воспроизвести условную схему CLI, задайте RETRIEVAL_MODE=conditional;
solution.py для платформы уже задаёт её явно вместе с USE_EMBEDDINGS=1.
Команды /new (очистить сессию) и /exit (выйти).
Обычные режимы --question и --question-file сохраняются.

ПРАВИЛА

- «Повтори ответ», «Повтори предыдущий ответ», «Можешь повторить свой ответ?»:
  в живой сессии возвращается тот же сохранённый ответ с теми же ссылками.
  На этот запрос не вызываются поиск, эмбеддер, реранкер и генератор.
  Общая первоначальная индексация базы, разумеется, остаётся.

- Повтор ответа из переданной извне истории также не запускает поиск.
  Реплика помечается как текст истории без проверки по базе. Пользовательские
  ID вида [S0001] не превращаются в подтверждённые ссылки; они удаляются при
  таком повторе. Существующая очистка команд ИИ/секретов применяется к тексту.
  Слишком длинный ответ не обрезается: система просит указать нужную часть.

- «Ответь на предыдущий вопрос» и «Ответь на вопрос выше» означают новый ответ,
  а не копирование. Восстанавливается предыдущий содержательный запрос
  с темой, датами, суммами и идентификаторами; обычный RAG выполняется снова.
  Промежуточные команды повторения не становятся новым предметом поиска.

- «А по ПТ-05/2023?» после вопроса о другом договоре переносит тему вопроса,
  заменяет старый номер новым и запускает поиск. Для отдельных коротких
  уточнений («А сколько?», «А какой срок?», «Почему?») сохраняется контекст.

- /new в CLI или chat.clear() очищает историю. Текстовые маркеры переключения
  темы сбрасывают наследование предыдущих условий:
  «Новый вопрос:», «Другой вопрос:», «Новая тема:», «Теперь о другом:».

- Если нужной истории нет, возвращается уточнение без API-вызовов.
  Сам факт наличия индекса или прошлой CSV-строки не создаёт историю диалога.

- «Повтори ответ, но измени сумму ...» не является буквальным повтором:
  правило полного совпадения не срабатывает; сообщение идёт в обычный RAG.

ОГРАНИЧЕНИЯ
Это детерминированные правила для типичных коротких диалогов, не универсальное
понимание всех местоимений и скрытых отсылок. Фразы вроде «возьми второй случай
из позапрошлого сообщения» не разбираются специальным планировщиком.
Никакого дополнительного LLM-классификатора на входе не добавлено.
Реплики ассистента сохраняются для разговора, но не становятся правовыми
основаниями и не подставляются как факты в поисковый запрос.
Генератор по-прежнему обязан обосновывать новый ответ документами базы.
Тестовые баллы и время полного прогона организаторов пока не измерены.

ПРОВЕРКИ
tests/test_dialogue.py: повтор без API, повторное решение вопроса,
сохранение сумм/дат, замена контрагента/договора, отсутствие истории,
изоляция сессий, очистка, ограничения памяти, защита кэша от изменения
выданного объекта, интерактивный CLI.
tests/test_submission_package.py дополнен запуском ZIP с разными ID:
повтор из истории, повтор без истории, новый ответ на предыдущий вопрос.
Только последний из этих трёх случаев обращается к модели ответа.
Существующие conditional/single_pass/pipeline проверки сохраняются.
Всего прошли 63 релевантные проверки: 19 dialogue, 17 single_pass,
13 conditional, 11 pipeline и 3 запуска ZIP. Проверки используют локальные
стабы, а не модели организаторов.
На всех 79 сохранённых вопросах совпали поисковые строки и полный порядок
BM25 с исходным 5d7f10d. Все 342 исходных чанка, тексты поиска и записи
источников тоже совпали. Это проверка отсутствия регрессии в этой части,
а не измерение баллов генератора или доказательство для скрытых вопросов.
Старый StubEngine в test_pipeline дополнен уже существующими в dev_if_test
полями retrieval_mode, conditional_threshold и vectors; код поиска из-за
этого устаревшего тестового стаба не менялся.

Эксперимент codex/vector-multi-query
Основа: dev_if_test, 5d7f10d (сообщённый результат 35/100).
Эта ветка независима от chunk-boundaries-fix: прежние 342 чанка,
их текст, индекс BM25, реранкер, порог 0,5 и генерационный промпт сохранены.

Пайплайн
1. Исходный поисковый запрос → прежний BM25 → реранкер.
2. При уверенном результате никаких дополнительных запросов модели нет.
3. Если оценка <0,5 и векторный индекс доступен, один запрос LLM генерирует
   две альтернативные формулировки. Передаётся вопрос и имеющийся диалог;
   предыдущие ответы ассистента не считаются подтверждёнными фактами.
4. Исходный вопрос всегда сохраняется. Альтернативы с изменёнными числовыми
   обозначениями, номером договора или названием в кавычках отбрасываются.
   Одинаковые формулировки удаляются. Это не проверка смысловой эквивалентности:
   сохранность всех условий/отрицаний обеспечивается промптом, но не доказана.
5. Эмбеддинги исходного и оставшихся альтернатив отправляются одним пакетом
   в существующий API. Индекс документов заново для вопроса не строится.
6. Для каждого вектора локально вычисляется ранжирование. Берётся до 64
   результатов каждого списка; объединение по ID и RRF 1/(60+rank).
   После объединения остаётся прежний лимит 64 кандидата.
   При равенстве учитываются позиция в исходном запросе и стабильный индекс.
7. Один отдельный векторный реранкер оценивает этот пул по исходному
   поисковому вопросу. Результат заменяет BM25-пул, как в dev_if_test.
   BM25-баллы не смешиваются с векторными или с RRF.
8. Прежнее расширение контекста и одна генерация ответа.

Ограничение времени и откат
Переформулировка: до 384 выходных токенов, без сетевого повтора.
QUERY_REWRITE_TIMEOUT_SECONDS по умолчанию 6; фактический бюджет не больше
30% оставшегося времени поиска. Если осталось меньше 3 секунд, шаг пропускается.
Общий существующий бюджет поиска 20 секунд и бюджета ответа не увеличивается.
При ошибке/тайм-ауте/некорректном JSON сохраняется поиск по исходному вопросу.
При ошибке пакетных эмбеддингов пробуется исходный запрос в оставшийся бюджет.
Если векторная ветка не завершилась, сохраняется уже ранжированная BM25-выдача.

Включение
solution.py принудительно задаёт DENSE_MULTI_QUERY=1, USE_EMBEDDINGS=1,
RETRIEVAL_MODE=conditional. При прямом импорте ядра DENSE_MULTI_QUERY=0
по умолчанию, чтобы воспроизводить контрольный вариант.
Реранкер берётся из RERANKER_MODEL, как в исходной сборке.

Расходы и ограничения
При слабом результате добавляется максимум один HTTP-запрос к генератору
для переформулировок. Один запрос эмбеддингов содержит до трёх входных текстов.
Число вызовов реранкера в нормальном пути не увеличено: один BM25 и один dense.
Локальные скалярные произведения обрабатываются без отдельных сетевых запросов
и без Python-потоков, которые не ускоряют эти CPU-циклы.
Исходный кандидат может потерять позицию после RRF; рост качества не гарантирован.
Почти одинаковые формулировки могут дать ту же выдачу с дополнительной задержкой.
Длительность полного прогона и оценка организаторов пока не измерены.

Наблюдаемость и проверки
Метрики содержат dense_multi_query, query_rewrite, число принятых запросов,
число уникальных кандидатов и размер пула после ограничения, причину отката.
pipeline_calls по-прежнему считает генерации ответа; все API-вызовы, включая
переформулировку, видны в api_calls и сумме токенов.
Тесты проверяют отсутствие рерайта на уверенной ветке, неизменность идентификаторов,
дедупликацию, объединение различных результатов, пакет эмбеддингов, исходный вопрос
реранкера, ограничение бюджета и сохранение BM25 при сбое.
ZIP проверяется запуском настоящего solution.py с локальным HTTP-сервером:
один уверенный и один слабый вопрос, три формулировки в одном запросе эмбеддингов.
Онлайн-модели и официальный тест для этих проверок не использовались.

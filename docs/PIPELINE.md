# Однопроходный пайплайн и границы проверки

## Основной путь

`solution.py` → `legal_core.run_submission()` → `submission_runner`.
CLI и runner используют `LegalAssistant.answer()`. По умолчанию он создаёт
новый `SinglePassPipeline` на запрос; состояние вопроса между ID не переносится.
`PIPELINE_MODE=adaptive` явно включает старый `AdaptivePipeline`.

Индексы и связи строятся один раз на экземпляр `LegalAssistant`. Метаданные
`source_records` также готовятся один раз, используются для поиска и контекста.
Исходный документ и смещения остаются доступными, чистка инструкций применяется
к представлению для модели. Эвристическая чистка не является полной защитой
от prompt injection и может не распознать новую атаку.

Запрос очищается; последняя реплика определяется до чистки, чтобы удалённая
команда в конце диалога не заставила отвечать на старый вопрос. Поисковый запрос
сохраняет реквизиты предыдущих пользовательских реплик, но не утверждения
ассистента. Поддержанный текстовый формат истории: `Пользователь:` / `Ассистент:`.

Лексический поиск ранжирует исходные положения с морфологическими вариантами,
триграммами и реквизитами. Кавычки не исключают слова из запроса. При явном
включении эмбеддингов добавляется второй список. RRF объединяет ранги, затем
опциональный cross-encoder API получает до `RETRIEVAL_CANDIDATES` кандидатов.
После этого выбирается `TOP_K`, добавляются ограниченные связи документов,
локальные ссылки на пункты и соседние части длинного положения.

Генерация читает упакованные оригиналы и метаданные напрямую, без промежуточного
графа фактов. У пакета два ограничения: сериализованный объём записей источников
и число источников. Бюджет символов — не точный бюджет токенов; вопрос, история,
системный промпт и ожидаемый ответ тоже должны помещаться в окно выбранной модели.
Отдельного обязательного вызова «достаточно ли оснований» нет.

## Что проверяется после генерации

- Ссылки допускаются только на источники, действительно переданные генератору.
- Неизвестные ID удаляются с сообщением о проблеме. Существующие ссылки и текст
  не заменяются вымышленными доказательствами.
- Заголовки I/R/A/C нормализуются, если распознаны все четыре секции.
- Длинные цитаты в кавычках сравниваются с текстом источников; несовпадения
  записываются в событие `validation`, не интерпретируются как доказанная ложь.
- Очевидные инструкции/секреты фильтруются тем же фильтром данных.

Валидные ID **не доказывают**, что утверждение следует из источника. В новом
режиме нет отдельного смыслового судьи и нет проверки всех чисел/дат по графу.
Это осознанное устранение дорогого обязательного этапа, требующее сравнения
качества. Ответ с проблемой формата/ссылок получает `partial`, а не автоматически
превращается в «оснований нет». Плохой формат может снижать официальный балл.
`answered`, `partial`, `insufficient`, `clarification`, `technical_error` —
операционные статусы, не оценка юридической правильности.

## Дедлайны и исполнение

Дедлайн пакета — абсолютное время `perf_counter`, заданное до чтения базы.
Он явно передаётся каждому worker через `DEADLINE`, поскольку обычные потоки
не наследуют `ContextVar`. Отдельный `Trace` ограничивает длительность вопроса.
Дедлайн опционального поиска дополнительно ограничен и восстанавливается перед
генерацией, оставляя ей оставшийся бюджет вопроса.

Каждый HTTP-вызов выполняется через `httpx.AsyncClient` под `asyncio.wait_for`;
синхронный интерфейс `ModelProxy` запускает этот вызов в собственном event loop.
`LegalAssistant.answer` остаётся синхронным: из async-приложения его следует
вызывать в рабочем потоке. Таймаут охватывает получение всего тела ответа.
Повторы временных ошибок делят бюджет одного вызова; 4xx кроме 429 не повторяются.
Технические ошибки не превращаются в юридические ответы.

Runner держит не больше `MAX_WORKERS` активных задач и не заполняет очередь
всем набором сразу. CSV атомарно обновляется после каждой готовой строки; порядок
ID остаётся исходным. Просроченные/необработанные строки явно технические.
Это не делает незавершённый пакет успешным, но сохраняет результаты остальных
вопросов и даёт диагностику. Резерв времени нужен для закрытия файлов.

ОС всё ещё нужна для внешнего лимита процесса: Python не может гарантировать
остановку любого произвольного кода рабочего потока или зависшего файлового I/O.
Сетевые запросы данного ModelProxy имеют проверяемый общий дедлайн.

## Сравнение

`experiments/evaluate_frozen_retrieval.py` измеряет попадание размеченных оснований
в фактический контекст выбранного режима. Этот скрипт отключает эмбеддинги и
реранкер даже при заданных ключах. Он не оценивает генерацию.

`experiments/compare_pipelines.py` сохраняет три вида результатов:

1. `single_pass` — новый поиск/контекст и прямой ответ;
2. `adaptive` — прежний модельный цикл с текущим общим ретривером;
3. `oracle` — прямой ответ по вручную заданным правильным источникам без поиска.

`adaptive` не является точным повтором исторического коммита: общий ретривер и
сетевой клиент тоже обновлены. Для точного сравнения старого кода используйте
исходный коммит отдельным запуском. Для проверки полезности векторов/реранкера
повторяйте `single_pass` с нужными настройками и отдельными отчётами.

Никаких автоматических оценок «правильно» скрипт не выставляет. Ручная оценка
должна отдельно учитывать полноту, правильность, доказательность ссылок и отказы.
Запуски сравнения последовательны; время набора на площадке измеряется через
`solution.py`, с её ограничениями и фактическим API.

## Условия следующего реального прогона

Нужны база `kb.zip`, актуальные вопросы/разметка, разрешённый API и его модель,
лимиты запросов и правила упаковки площадки. В этом репозитории они не сохранены.
Образ Docker отсутствует; сборщик создаёт ZIP с корневыми модулями и requirements.
Реальная скорость, расход и официальный балл новой версии ещё не измерены.

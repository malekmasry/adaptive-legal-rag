# Локальный стенд калибровки ПСБ, v2

Цель: проверить, воспроизводит ли локальная оценка различия между известными
версиями RAG, прежде чем оптимизировать по ней новые версии. **Реальные ответы
четырёх версий получены; итог — в `RESULTS.md`.** Нельзя объявлять калибровку достигнутой по числу
вопросов, тестов кода или совпадению одного балла.

## Эта ветка

Ветка `psb_rag_benchmark` создана от `main`; бенчмарк находится целиком в
`benchmarks/psb_v2/`. Корпус, четыре замороженных снимка runtime и сохранённый
эксперимент включены. Производственный пайплайн в корне не изменён.

```bash
git clone --branch psb_rag_benchmark https://github.com/malekmasry/adaptive-legal-rag.git
cd adaptive-legal-rag/benchmarks/psb_v2
python3 -m venv .venv
source .venv/bin/activate
python3 -m pip install -r requirements.txt
python3 benchmark.py validate
python3 -m unittest -q test_calibration.py
```

Эти проверки не вызывают платные API. Для настоящего прогона настройте приватный
файл сервисов по инструкции ниже. Итог предыдущего опыта — `RESULTS.md`;
машиночитаемый отчёт — `experiment/report/calibration.json`.

## Данные

111 вопросов: 18 официальных демонстрационных, 63 development, 30 старых
отложенных. К прежним 90 добавлена 21 разговорная/диалоговая формулировка.
Это дополнительные варианты прежних семейств, **не 21 независимый новый факт**.
Все варианты одного семейства остаются в одном split. Исходные ответы,
документы и точные диапазоны доказательств сохранены. Сложность не подбиралась
по ответам четырёх версий: формулировки зафиксированы до их получения.

Новые формулировки сохраняют достаточные условия задачи, но уменьшают прямое
лексическое совпадение, используют падежи, разговорную речь, историю,
ложные предпосылки и похожие имена. Разметка требует независимой проверки:
программная проверка цитат не доказывает правильность самого эталона.

После генерации обнаружена одна ошибка эталона S12c: вопрос «можно ли обойтись
без одобрения» унаследовал «Да» от противоположной формулировки. Исправление
«Нет, нельзя» записано отдельно в `label_errata.json`, проверяется по исходному
документу и применяется `labels.py`. Исходный `cases.jsonl` и его хеш сохранены.
Для всех четырёх версий этот вопрос переоценён; тексты вопросов, необходимые
факты, доказательства и веса не менялись. `cases_effective.jsonl` — удобный
экспорт исправленной разметки, не новый набор вопросов.

30 старых отложенных вопросов зарезервированы, но **не объявляются никогда
не использовавшимися ранее**. Для окончательной проверки переноса нужны новые
семейства или будущая версия RAG с ещё неизвестным баллом. Если по контрольному
набору исправляют код/вопросы/судью, он становится development.

## Что исправлено в измерении

1. `run_matrix.py` запускает реальный `solution.py` из зафиксированного снимка.
   Импорт `engine.answer()` обходил флаги entry point. Теперь reviewer и
   evidence-coverage включаются ровно своим entry point, старые флаги оболочки
   не переносятся между запусками. Проверяются фактические вызовы реранкера
   и использование/готовность dense-поиска.
2. Судья получает ответы A/B без имён сборок и известных баллов. Общий baseline
   создаётся один раз и используется для всех версий. Каждый вопрос оценивается
   в двух порядках. Golden используется только судьёй, не генератором.
3. Судья отличает гипотетические условия от утверждений пользователя о договоре.
   Для обнуления за выдумку требуется цитата именно из ответа и буквальная
   цитата из исходного документа. Это проверка происхождения, не независимое
   доказательство юридической применимости; сомнения оставляются `needs_review`.
   Судья также получает фактические контексты обоих RAG, восстановленные из логов.
   Правдивое замечание об отсутствии нормы в выдержках не превращается в выдумку
   только потому, что норма есть в полном документе. Выбор A/B/ничья переводится
   в число кодом; преимущество требует существенной диагностированной ошибки.
4. Спорные/неоценённые случаи видны в coverage и границах итогового балла:
   показывается результат, если все неизвестные окажутся поражениями или
   победами. Сравнение проводится на общих успешно оценённых вопросах;
   при покрытии ниже 95% стенд не подтверждает воспроизведение порядка.
5. Проверяются одинаковые судья, промпт, baseline, корпус, набор вопросов и
   конфигурация сервисов. Несопоставимые результаты не объединяются в рейтинг.

Это приближение опубликованной процедуры ПСБ: `100 × (0.7 MR + 0.3 WR)`.
Чужие baseline, golden и судья неизвестны. Поэтому локальные 50 или 80 сами по
себе не означают 50 или 80 на площадке. Число найденных пунктов также не является
баллом за юридический ответ.

## Как решаем, что тест полезен

До получения ответов фиксируем сценарии, рубрику и одинаковую методику подсчёта.
Основная цель — порядок `35 > 29 > 22,57 > 14` и правильное направление разрывов.
Отчёт показывает ранговую корреляцию, каждый разрыв, bootstrap по семействам,
ошибки по категориям и покрытие. Различия без устойчивости по семействам не
считаются надёжными. Повтор идентичной сборки оценивает шум генерации/судьи;
без него неизвестно, насколько стабильны даже официальные четыре числа.

Линейная привязка локальных баллов к официальным — только диагностическая.
Для каждой версии она строится по остальным трём, затем предсказывается
оставленная. Показывается ошибка leave-one-version-out. Хорошее совпадение
четырёх исторических точек не доказывает прогноз новых версий: окончательная
проверка — заранее записанный прогноз для новой сборки и затем результат ПСБ.
Приблизительный балл 35 ограничивает точность такой привязки.

Не подбираем веса категорий и отдельные вопросы так, чтобы принудительно
получить нужные четыре числа. При несовпадении разбираем реальные ответы,
ошибки эталона, судьи, конфигурации и отсутствующие типы заданий. После правок
нужна проверка на отложенных данных; старое совпадение не засчитывается повторно.

## Запуск

Python 3.11+, `httpx==0.28.1` для самих RAG; для локальной оркестрации также
нужен NumPy. BGE-процесс требует PyTorch и Transformers. Запускайте команды
из каталога стенда. Если рядом уже есть `frozen/`,
снимки четырёх версий подготовлены. Иначе:

```bash
python3 run_matrix.py freeze --repo /path/to/adaptive-legal-rag --output frozen
python3 benchmark.py validate
python3 -m unittest -q test_calibration.py
```

В копии `services.example.json` задаются точные адреса/имена моделей и ключи.
Храните заполненный файл вне репозитория. Обязательны явные `LLM_MODEL`,
`EMB_MODEL`, `RERANKER_MODEL`. Отдельному хосту требуется отдельный ключ.
Параметры генерации не меняйте между версиями. Конфигурация исторических
прогонов должна быть подтверждена Маликом; повторно присылать ключи не требуется.
Только после подтверждения выставляется `historical_config_confirmed=true`
в `anchors.json` и заново создаются снимки через `freeze` в новый каталог.
Совпадение порядка на пилоте или с неподтверждённой конфигурацией отображается
как диагностическое совпадение, но не как подтверждённая калибровка.

```bash
python3 run_matrix.py run --frozen frozen --version vector14 \
  --services /path/to/private-services.json --output runs/vector14-dev
python3 run_matrix.py run --frozen frozen --version coverage2257 \
  --services /path/to/private-services.json --output runs/coverage2257-dev
python3 run_matrix.py run --frozen frozen --version review29 \
  --services /path/to/private-services.json --output runs/review29-dev
python3 run_matrix.py run --frozen frozen --version conditional35 \
  --services /path/to/private-services.json --output runs/conditional35-dev
```

`--split holdout` — отдельный контрольный прогон. Для пилота задайте одинаковые
`--ids S01a,S01c,S09a,S09c,S17a,S17c,S20a,S20c,S21a,S21c,S24a,S24c` во всех
запусках и в `judge_batch.py`. Пилот включает разные типы ошибок, но не даёт основания
объявить весь бенчмарк откалиброванным. Сначала пилот, затем полный набор.
Прерванные результаты не перезаписываются; для повтора нужен новый каталог.

В `judge_batch.py` модель судьи задаётся через `--model`; адрес и ключ берутся
из приватного файла сервисов. Предпочтителен другой проверяющий или ручная проверка выборки. Использование
того же DeepSeek допускает коррелированные ошибки и требует отдельного контроля.
Один baseline для всех четырёх — `runs/vector14-dev/submission.csv`:

```bash
python3 judge_batch.py --candidate runs/review29-dev/submission.csv \
  --baseline runs/vector14-dev/submission.csv --split development \
  --services /path/to/private-services.json --model qwen3.8-max \
  --output judgments/review29.jsonl
```

`judge_batch.py` автоматически применяет исправления эталонов и записывает их
хеш. Прямой CLI старого `judge.py` сохранён для аудита исторического опыта:
он читает исходную разметку без errata и не является рекомендуемой точкой запуска.
Изменённый runner не дописывает старые результаты с другим хешем: для нового
прогона нужен новый выходной каталог.

Аналогично оцениваются остальные три версии, включая baseline против самого
себя: при одинаковом ошибочном ответе правило выдумок всё ещё может дать ноль.
Всего полный development требует 252 генерации и 504 судейских вызова,
плюс реранкинг/эмбеддинги/внутренние проверки. Это число вызовов, не стоимость;
фактический расход зависит от контекстов, ответов, повторов и выбранных API.

Пакет реального опыта включает `seed_embeddings/` для проверки совместимости
индекса. Веса на 2.27 GB не включены; `download_bge.py` скачивает фиксированную
официальную ревизию и проверяет хеши. В опыте использованы Linux CPU,
`torch==2.15.0+cpu`, `transformers==4.57.6`, `tokenizers==0.22.2`, `numpy==2.5.4`.
Параметры локальной BGE в приватном файле конфигурации:
`EMB_BASE_URL=http://127.0.0.1:8769/v1`, `EMB_API_KEY=local-bge-cache`,
`EMB_MODEL=BAAI/bge-m3`. Это локальный технический ключ, не ключ внешнего API.

```bash
python3 download_bge.py
python3 live_run.py --services /path/to/private-services.json --frozen frozen \
  --weights ../bge_model/5617a9f61b028005a4858fdac845db406aefb181 \
  --seed seed_embeddings --dependency-path "" --output runs/development
python3 judge_controls.py --services /path/to/private-services.json \
  --runs runs/development --output controls.json
python3 judge_matrix.py --services /path/to/private-services.json \
  --runs runs/development --output judgments --workers 4 --parallel-versions 2
python3 retry_unresolved.py --services /path/to/private-services.json \
  --runs runs/development --input judgments --output judgments-resolved
```

Пустой `--dependency-path` предполагает, что зависимости BGE установлены в
том же Python-окружении. При отдельной установке туда передаётся путь к её
пакетам. `live_run.py` держит локальный сервис и дочерние решения в одном
сетевом окружении. Ключи остаются в отдельном приватном JSON, вне архива.
Повтор судейства выполняется один раз для каждого неопределённого результата;
валидные низкие оценки не перезапускаются. Исходные попытки сохраняются.

В сохранённом опыте финальный каталог — `experiment/judgments-completed/`.
Предыдущие слои сохранены для аудита: `judgments-final` — первая оценка по
финальной рубрике, `judgments-resolved` — один повтор спорных решений,
`judgments-corrected` — исправление S12c у всех версий, `judgments-completed` —
дозапрос раундов, не полученных при транспортном сбое. Старые `judgments` и
`judgments-v2` используют отменённые версии судьи и в итог не входят.
`rejudge_errata.py` нужен только для старых оценок до исправления меток;
новый `judge_batch.py` уже использует errata.

```bash
python3 calibrate.py --split development --output calibration-dev.json \
  --judgments vector14=judgments-resolved/vector14.jsonl \
  coverage2257=judgments-resolved/coverage2257.jsonl review29=judgments-resolved/review29.jsonl \
  conditional35=judgments-resolved/conditional35.jsonl
```

## Перед работой агентов

Сначала подтверждаем воспроизводимость и качество измерителя. Агентам выдаём
только development и конкретные ошибки; контрольные ответы не включаем в их
рабочие копии. Отдельно фиксируем контрольную сборку, модель, корпус, конфиг,
лимит времени и бюджет API. Каждый агент проверяет одну гипотезу; готовые
изменения сравниваются с контрольной сборкой на тех же вопросах. Решающая
проверка проводится отдельно на контроле и новой отправке ПСБ.

Архив стенда содержит ответы и должен храниться отдельно от submission.
Организационное разделение файлов само по себе не создаёт технической изоляции
агентов: для действительно скрытого контроля нужен отдельный evaluator.
